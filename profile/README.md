<p>小流量试跑失败的时候，最容易做的动作是"再换一条线试试"，换到第五条还是不行，才发现问题根本不在线路上。故障树的价值就是让你在动手之前先分类：连不上、连上被拦、跑着掉线、跑顺但慢，四条主干的成因和处置完全不同，混着处理只会把简单问题拖成多线排查。</p>

<h2>一、顶层事件与四条主干</h2>
<p>顶层事件定义为"小流量试跑未通过"。往下分四条主干：根本连不上、能连但立刻被要求验证、跑一段时间掉线、跑得顺但明显慢。四条之外还有一个横向分支：归属地与预期不符，它可能在任何阶段出现。</p>

<h3>为什么先分类再动手</h3>
<p>四类问题的处置方向互斥。连不上时换城市毫无意义，被拦时换端口也没用。先归到某一类，再按该类的最小动作试一次，比盲目换线快得多，也不会在换线过程中把原本可用的线路丢掉。</p>
<h3>横向分支别漏掉</h3>
<p>归属地不符不是独立故障，而是一个会在任何阶段冒出来的问题。查法很简单：拿到 IP 后查注册地和 ASN，与订单上的城市比对。不符就不用往下查了，直接联系供应商。</p>

<h2>二、主干一：根本连不上</h2>
<p>连不上是第一层最干脆的故障，也是最容易定位的。按本地、鉴权、端口、上游四层逐层排除，每层只做一个动作。</p>
<p>先确认本地能出网：不挂代理直接访问一个普通网站，通了说明本地链路没问题。再确认代理配置：地址、端口、用户名密码逐字比对，尤其注意密码里的特殊字符是否被转义。</p>
<h3>鉴权失败的三种表现</h3>
<p>一是握手后立刻断开，通常是账号密码错；二是能连但所有请求返回 407，是认证方式不匹配；三是时通时不通，是同一账号被多端占用触发了并发限制。三种表现对应三种改法，别混着试。</p>
<h3>端口被封怎么判断</h3>
<p>同一地址换一个端口能通、原端口不通，基本可以确定是端口层面的问题。这种情况下换端口比换线路快，且不影响已经配好的会话环境。</p>

<h2>三、主干二：连上就被要求验证</h2>
<p>这一类最容易被误判成"线路坏了"。实际上线路是通的，只是环境的一致性没对上，或者出口属性不符合预期。查的顺序是：地区、属性、时区、语言。</p>

<h3>地区一致但属性不对</h3>
<p>常见情况是 IP 注册城市没错，但 ASN 指向数据中心。这种地址在归属查询里看着像本地，实际属性是机房段。查法是看 ASN 的名称，运营商名称与数据中心服务商名称的区别很明显。</p>
<h3>时区与语言这两个低级错</h3>
<p>出口在洛杉矶、浏览器时区是东八区，这种组合在真实用户里极少出现。修正只需要改一个设置，但很多团队在批量部署时忘了逐台改，母版里带的默认值一路复制下去。</p>

<h2>四、主干三：跑一段时间掉线</h2>
<p>能连上、能登录、能对话，十几分钟或半小时后断开，这类故障八成出在会话保持上，而不是线路本身。先看断开的间隔是否规律，规律说明是超时或心跳问题。</p>

<h3>心跳间隔怎么定</h3>
<p>比服务端的空闲超时短一半比较稳妥。如果不知道服务端阈值，从两分钟开始试，逐步拉长到刚好不断开的那个值，再退回来一档留余量。</p>
<h3>自动重连要配，但不能掩盖问题</h3>
<p>自动重连能让任务继续跑，但如果断连频率高，重连只是把问题藏起来。正确做法是重连的同时记录次数和时刻，一周看一次趋势，频率上升就要查链路。</p>

<h2>五、观测时段怎么排、放量门槛怎么定</h2>
<p>小流量试跑最容易犯的错是只在白天试。白天链路空闲，什么问题都看不出来。观测时段至少覆盖三段，每段连续两天。</p>
<p>三段是：上午九点到十一点、晚上八点到十一点、凌晨两点到四点。三段的意义不同：第一段看业务高峰、第二段看家庭宽带最拥挤、第三段看无人值守时的稳定性。</p>
<h3>放量的三个量化门槛</h3>
<p>一是验证页出现率低于一成；二是晚间九十分位响应在三秒以内；三是连续两天没有同段两号同时异常。三条都满足再放量，缺一条就先修那一条，别抱着"先上再说"的心态。</p>
<h3>放量节奏</h3>
<p>每批加原有规模的三成，观察满二十四小时再加下一批。三成这个比例的好处是，出问题时影响范围可控，且新增号的异常能从旧号的表现里对照出来。</p>

<h2>常见问答</h2>
<h3>试跑三个号都失败，是不是供应商有问题？</h3>
<p>答：先按四条主干分类。如果三个号都是同一类失败，且换了本地环境依然复现，才可能是供应商侧的问题。三个号分属三类失败，多半是你自己的配置没统一。</p>
<h3>验证页出现一次就要换线吗？</h3>
<p>答：不必。偶发一次可以观察，关键是看频率和聚集性。同一时段集中出现、或同址多个号连锁出现，才说明需要换线或调整分组。</p>
<h3>凌晨时段没人值守，怎么观测？</h3>
<p>答：用脚本记录，不必人工盯。每小时跑一次轻量请求，记录耗时和状态码，第二天看汇总。重点是发现断连的时间规律，而不是实时响应。</p>
<h3>掉线自动重连算不算解决了问题？</h3>
<p>答：算缓解，不算解决。重连让业务不中断，但底层的链路问题还在。把重连次数当指标看，频率稳定在低水平可以接受，持续上升就要回头看主干三。</p>
